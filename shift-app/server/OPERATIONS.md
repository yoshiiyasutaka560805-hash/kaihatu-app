# 勤務表アプリ 社内サーバー版 運用手順書

対象：情報システム担当（情シス）、施設長（システム管理者）。
規模の想定：**サーバーを使うのは勤務表の作成関係者 約10名のみ**。全職員（約130名）はサーバーにログインしません（アカウントを作らない）。確定した勤務表は、アプリの出力（印刷・閲覧用HTMLファイル・Excel貼付用コピー）として配布します（4-5）。扱う情報：職員の勤務・休暇（個人情報）。

> **法令・指導に関する注意**：本書は技術的な運用手順です。個人情報の保管期間・委託・開示等の法的な扱いについては断定していません。**法人の個人情報保護方針（個人情報取扱規程）および指定権者（所管の自治体）の指導を確認**し、本書の「方針決定が必要な事項」を法人として決めてください。

## 1. 構成

```
 職員のPC/タブレット（社内LAN）
        │  HTTPS（社内CA証明書）
        ▼
 ┌───────────────────────────────┐
 │ [任意] リバースプロキシ           │   Linux: nginx   Windows: IIS(ARR)
 │  ・HTTPS終端／HSTS／アクセス元IP制限 │   → deploy/nginx.conf.example
 │  ・X-Forwarded-For を接続元で上書き │   → deploy/web.config.example
 └──────────────┬────────────────┘
                │ http://127.0.0.1:8443（同一サーバー内のみ）
                ▼
 ┌───────────────────────────────┐
 │ shift-app（Node.js 22、標準モジュールのみ）│  常駐: systemd / NSSM
 │  ・認証・権限判定・監査ログ（すべてサーバー側）│
 └──────────────┬────────────────┘
                ▼  DATA_DIR（専用アカウントのみ読み書き）
   users.json   months/   backups/   audit.log   audit/   sessions.json
                │
                └─ 日次 backup.sh / backup.ps1 ─▶ 別媒体（NAS・別サーバー・暗号化USB等）
```

- インターネットへは一切出さない（外部通信・CDN・外部フォントなし）。ポート開放・クラウド公開は禁止。
- プロキシなしで本サーバー自身がHTTPSを受ける構成も可（`TLS_CERT` / `TLS_KEY`）。社内に IIS / nginx の運用実績があるならプロキシ構成を推奨（IP制限・ログ・証明書更新を既存の仕組みに載せられるため）。
- 社内サーバーの種類（Windows / Linux、IISの有無）が決まるまでは、**第3章の「共通」と、該当OSの節だけ**を読めば足ります。

## 2. 用意するもの

| 項目 | 内容 |
|---|---|
| Node.js 22 LTS | 情シスが入手・検証したインストーラ/パッケージ。以後のセキュリティ更新計画も決める |
| アプリ一式 | `kaihatu-app` フォルダ（`shift-app/index.html` と `shift-app/server/`）。`npm install` 不要 |
| 専用アカウント | Linux: `shift-app`（nologin）／ Windows: `svc_shiftapp`（ローカル低権限）。管理者/rootで動かさない |
| 証明書 | 社内CAが発行（CN/SAN=職員が使うホスト名 例 `shift.example.local`）。検証用のみ `deploy/make-selfsigned.sh` |
| 公開ホスト名 | 社内DNSに登録（例 `shift.example.local`） |
| バックアップ先 | 本体とは別の媒体・別の場所（NAS・別サーバー等）。暗号化とアクセス制限 |
| 時刻同期 | NTP（監査ログの時刻の正確さのため） |

## 3. 初期構築

### 3-A. 共通（先に決める）
1. 公開URL（例 `https://shift.example.local`）とアクセス許可するネットワーク（職員用VLAN等）を決める。
2. 最初の管理者（施設長 = `admin`）の職員IDを決める（例 `admin01`。共有IDは作らない）。
3. 下記「方針決定が必要な事項」（第9章）を、構築と並行して決裁に回す。

### 3-B. Linux（systemd ＋ nginx）
```
# 1) 専用ユーザーと配置（root）
useradd --system --home-dir /var/lib/shift-app --shell /usr/sbin/nologin shift-app
cp -r kaihatu-app /opt/kaihatu-app            # root所有・読み取りのみでよい
install -d -o root -g shift-app -m 0750 /etc/shift-app
cp /opt/kaihatu-app/shift-app/server/deploy/env.example /etc/shift-app/env
chown root:shift-app /etc/shift-app/env; chmod 0640 /etc/shift-app/env
#   → /etc/shift-app/env を編集（PUBLIC_ORIGIN、TRUST_PROXY=1、SECURE_COOKIE=1 など）

# 2) サービス登録・起動
cp /opt/kaihatu-app/shift-app/server/deploy/shift-app.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now shift-app
systemctl status shift-app                    # active (running) を確認

# 3) 最初の管理者（初期パスワードは画面に一度だけ表示。控えは安全な方法で本人へ）
sudo -u shift-app env DATA_DIR=/var/lib/shift-app \
  node /opt/kaihatu-app/shift-app/server/adduser.js admin01 "施設長" admin "*"

# 4) nginx（HTTPS終端）
cp deploy/nginx.conf.example /etc/nginx/conf.d/shift-app.conf   # 証明書パス・ホスト名・許可IP帯を編集
nginx -t && systemctl reload nginx

# 5) バックアップ（日次）: cron 例（毎日2:30）。退避先は別媒体
#   30 2 * * *  shift-app  /opt/kaihatu-app/shift-app/server/deploy/backup.sh /var/lib/shift-app /mnt/backup/shift-app 14
```
- `adduser.js` は **必ず `sudo -u shift-app` で実行**（rootで実行するとデータファイルがサービスから読めなくなる）。
- nginx は `X-Forwarded-For` を `$remote_addr` で**上書き**している（`nginx.conf.example`）。この行を変えない。

### 3-C. Windows（NSSM ＋ IIS または直接HTTPS）
1. 情シスが入手・検証した `nssm.exe` を任意の場所（例 `C:\tools\nssm.exe`）に置く（スクリプトは自動ダウンロードしません）。
2. 専用ローカルアカウント `svc_shiftapp` を作成（一般ユーザー権限。「サービスとしてログオン」を許可）。
3. 管理者PowerShellで、まず**確認のみ（-DryRun）**：
```
.\install-windows.ps1 -AppDir C:\kaihatu-app -DataDir D:\shift-app-data -NssmPath C:\tools\nssm.exe `
   -ServiceAccount .\svc_shiftapp -ReverseProxy -PublicOrigin https://shift.example.local -DryRun
```
   内容を確認し、`-DryRun` を外して実行（アカウントのパスワードは実行時に入力。スクリプトには書かない）。
4. IIS を使う場合：URL Rewrite と ARR を導入し、`deploy/web.config.example` をサイト直下へ（ファイル内のコメントの前提作業・`X-Forwarded-For` 上書き設定を確認）。HTTPS バインディングに社内CA証明書を設定。IISを使わない場合は `-ReverseProxy` の代わりに `-TlsCert/-TlsKey` と `-AllowedRemote 192.168.x.0/24` を指定して直接HTTPS。
5. 最初の管理者を作成（`svc_shiftapp` で実行するか、作成後に `DATA_DIR` のACLを再適用）：
```
$env:DATA_DIR='D:\shift-app-data'
& 'C:\Program Files\nodejs\node.exe' C:\kaihatu-app\shift-app\server\adduser.js admin01 "施設長" admin "*"
```
6. `backup.ps1` をタスクスケジューラに日次登録（実行アカウントは DataDir 読取・退避先書込可）：
```
powershell -ExecutionPolicy Bypass -File C:\kaihatu-app\shift-app\server\deploy\backup.ps1 -DataDir D:\shift-app-data -Dest \\nas\backup\shift-app -Keep 14
```

### 3-D. 動作確認（共通）
- ブラウザで公開URLを開き、鍵マーク（警告なし）を確認 → 管理者でログイン → **パスワード変更が求められる**ことを確認 → 変更後、サンプルデータで保存・再読込。
- 別PCから、許可していないネットワーク（例 来客用Wi-Fi）から**開けない**ことを確認。
- サーバーを再起動しても、有効期限内ならログインが維持されることを確認（勤務中の再起動の影響を小さくするため）。
- 監査ログ（`audit.log`）にログイン・保存が記録され、パスワードや勤務内容が含まれないことを確認。

## 4. ユーザー管理

以降のコマンドは、Linuxなら `sudo -u shift-app env DATA_DIR=/var/lib/shift-app node /opt/kaihatu-app/shift-app/server/adduser.js …`、Windowsなら `$env:DATA_DIR` を設定して `node …\adduser.js …`。以下は `adduser.js …` と略記。サーバー再起動は不要。

### 4-1. 権限の割当方針（推奨）
| 立場 | role | グループ（＝勤務表の部署名） | できること |
|---|---|---|---|
| 施設長・システム管理担当（最少人数） | `admin` | 全部署（`*`） | 全部署の閲覧・更新、**監査ログ閲覧**、月の共通設定、**確定・確定解除（常に可）** |
| **勤務表の作成関係者（約10名・全員）** | `editor`（編集者） | 全部署（`*`。省略可） | 全部署の閲覧・更新（取込・自動作成・出力も可）。監査ログ閲覧は不可。確定・確定解除は**権限フラグがある場合のみ** |
| （必要時のみ）フロア限定の担当 | `manager1` / `manager2` | 自フロア | manager1＝全部署を閲覧・自フロアのみ更新 / manager2＝自フロアのみ閲覧・更新 |
| （通常は登録しない）照会のみ | `staff` | 自フロア | 自フロアの閲覧のみ |

- **推奨**：作成関係者10名＝全員 `editor`、施設長＝`admin`（監査ログの確認・確定）、確定できる人は `--grant finalize` で付与（4-4）。全職員（約130名）にはアカウントを作りません（配布は出力ファイル。4-5）。
- 原則は「必要最小限」。迷ったら権限の低い方にする。`admin` は施設長と代行者1名程度に限定。`editor` は全部署の勤務・氏名を見られるため、作成に必要な人だけにする。
- グループ名は勤務表の部署名と**完全一致**（例 `2階`）。
- 兼務は `2階,3階` のように複数指定。IDは1人1つ（共有ID禁止）。

### 4-2. 追加
```
adduser.js k.tanaka "（氏名）" editor '*'      # 作成関係者（全部署の編集者）。初期パスワードが一度だけ表示される
```
- 初期パスワードは本人にだけ安全な方法（対面・内線等。メール・チャット不可）で伝える。**初回ログイン時に本人が変更必須**。
- 一括登録はCSV（列：職員ID,氏名,ロール,グループ（`;`区切り。`admin`/`editor` は空欄可））。作成関係者の10名程度に使います：既定の想定はここまでで、全職員の登録は不要です。
```
adduser.js --csv staff.csv --dry-run      # 検証のみ（不正があれば全件登録しない）
adduser.js --csv staff.csv --out pw.tsv   # 初期パスワード一覧を 0600 のファイルにのみ出力
```
  `pw.tsv` は配布後に**安全に削除**。画面表示（`--out` なし）の場合は端末の画面履歴・スクロールバックも消す。CSV自体も職員名を含む個人情報なので、作業後に削除する。

### 4-3. 退職・異動
```
adduser.js --disable k.tanaka      # 退職日（または異動日）に実施。ログイン中でも次の操作で失効
adduser.js --enable  k.tanaka      # 復職時
adduser.js --list                  # 一覧（[無効] [要PW変更] [確定権限] が表示される）
```
- **退職日当日に無効化**する運用を、人事の退職手続きに組み込む（人事→情シス/施設長への連絡ルートを明記）。
- 異動でフロアが変わる場合は無効化→新グループで再登録（グループ変更コマンドはないため）。
- パスワード忘失・漏えいの疑い：`adduser.js --passwd k.tanaka`（再発行。既存ログインは失効し、次回ログインで変更必須）。

### 4-4. 確定（ロック）の権限フラグ
```
adduser.js --grant  finalize k.tanaka    # 「確定」「確定解除」できる権限を付与（設定で付け外し可。誰に付けるかは法人で決める）
adduser.js --revoke finalize k.tanaka    # 取り消し（`admin` は常に可能）
```
- 付け外しはサーバー再起動不要で、ログイン中のユーザーにも次の操作から反映される。付与・取消の実施者・日付は運用記録に残す（人事・施設長の承認を得る）。
- 確定した月は**誰も保存できない**（サーバーが423で拒否）。確定時に下書きのバックアップを1世代必ず作成し、監査ログに `finalize` / `unfinalize`（誰が・いつ・どの月）を記録する（勤務内容は記録しない）。

### 4-5. 全職員への配布（出力ファイル）
1. 作成関係者が勤務表を完成させ、**「確定する」**（画面下部。エラーが残っていれば警告が出る）。
2. 「⑧ 出力」（またはヘッダーの「閲覧用ファイルを保存」「Excel用にコピー」「印刷」）で、配布用ファイルを出力する。**「休暇の伏せ方」**を確認する：
   - `機微なものだけ伏せる`（**既定・推奨**）：欠勤・産休・忌引・休職など→「休」。有休・リ休・誕休・研修などはそのまま表示。
   - `すべての休暇を伏せる`：休暇の種類を全て「休」にする（より保守的）。
   - `伏せない`：そのまま（作成関係者の内部確認用）。
   - 伏せ方はファイル配布前に、法人の方針で決める（有休などを見せてよいかも含む）。独自に追加した休暇記号は自動では伏せられないので、必要なら出力前に確認する。
3. 配布先は**施設内の共有フォルダ**等。閲覧できる範囲（フォルダのアクセス権）を、必要な職員だけに限定する。閲覧用HTMLのフッターには「社内限定・持ち出し・撮影禁止」を入れてある。
4. 配布ファイルの**保管期間・差し替え（確定を解除して修正した場合の旧版の回収・削除）**の手順を法人で決める。

### 4-6. 利用者向け案内
- 画面下部「パスワード変更」で自分で変更可能（12文字以上、職員ID・氏名を含めない、直近と同じ不可）。変更すると他の端末のログインは解除される。
- ログイン失敗が続くと10分間ロックされる（5回）。ロックはサーバー再起動でも解除されない。

## 5. 日常運用とログ点検

| 頻度 | 作業 |
|---|---|
| 毎日 | バックアップの成否確認（`backup.log` の最終行が「完了」か。失敗時は終了コード1で通知されるよう設定） |
| 毎週 | サービス稼働・ディスク空き容量の確認 |
| 毎月 | 監査ログの点検（下記）。バックアップからの読取テスト（tar/zip が開けるか） |
| 四半期 | **アクセス権の棚卸し**（`--list` と人事の在籍名簿を突き合わせ。退職者の無効化漏れ、権限過大の是正） |
| 半年〜年1回 | **復元訓練**（第6章）、OS・Node.js のセキュリティ更新、証明書の期限確認 |

### 監査ログの点検（毎月）
ログは `DATA_DIR/audit.log`（当月）と `DATA_DIR/audit/audit-YYYY-MM.log`（過去分）。1行1件のJSON。システム管理者は画面/API（`/api/audit`）でも直近を確認できる。
```
# Linux 例（件数が多いIPの確認、ロック・拒否の確認）
grep -h '"event":"login_fail"' /var/lib/shift-app/audit.log | grep -o '"ip":"[^"]*"' | sort | uniq -c | sort -rn | head
grep -hE '"event":"(login_locked|save_denied|password_change_fail)"' /var/lib/shift-app/audit.log | tail -50
```
```
# Windows 例
Select-String -Path D:\shift-app-data\audit.log -Pattern '"event":"(login_locked|save_denied|password_change_fail)"' | Select-Object -Last 50
```
見るポイント：
- 同一IP/IDの `login_fail` の連続、`login_locked`（不正アクセスや入力ミスの多発）
- 深夜・休日の `view` / `save`、普段使わない人の閲覧
- `save_denied`（権限外の保存の試み）、`audit_view`（誰が監査ログを見たか）
- 退職者・無効化済みIDでの `login_fail`
- 異常があれば、該当者への確認 → 必要なら `--passwd` / `--disable` → 施設長へ報告（記録を残す）。

記録される内容：誰が・いつ・どのIPから・何を（ログイン/閲覧/保存/パスワード変更）・どの月/部署。**パスワード・トークン・氏名・勤務内容は記録されない。**

### ログのローテーションと保管
- `audit.log` は月替わりまたは5MB超で `audit/audit-YYYY-MM.log` へ自動退避。
- **既定では古いログを削除しない**。保管期間を法人が決めたら `AUDIT_RETENTION_DAYS=（日数）` を設定すると、超過分を自動削除（起動時と6時間ごと）。
- 退避済みログもバックアップ対象（`DATA_DIR` 全体）に含まれる。バックアップ側の世代数・保管期間も同じ方針で揃える。

## 6. バックアップと復元（訓練を含む）

### 6-1. 二段構え
1. アプリ内蔵：保存のたびに `data/backups/YYYY-MM/` へ版ごとのコピー（月ごと直近30世代）。**同一ディスクのため、ディスク故障・誤削除には無力**。操作ミス（上書き・誤編集）の巻き戻し用。
2. 別媒体への退避（日次）：`deploy/backup.sh`（Linux）/ `deploy/backup.ps1`（Windows）。データ全体を世代管理（既定14世代）して別媒体へ。結果は退避先の `backup.log`。`sessions.json`（ログイン状態）は退避しない。

### 6-2. 復元手順A：特定の月を前の版に戻す（操作ミス）
1. その月の `data/backups/YYYY-MM/` から戻したい版のファイルを選ぶ（ファイル名に version と日時）。
2. `data/months/YYYY-MM.json` を、そのファイルで置き換える（サーバー停止は不要）。権限は実行ユーザーのみ（0600）。
3. 開いている画面は**再読込**してもらう（version が戻るため、古い画面からの保存は競合扱いになる）。
4. 誰が・なぜ戻したかを記録に残す。

### 6-3. 復元手順B：サーバー全体（故障・ランサム等）
1. サービスを停止（`systemctl stop shift-app` / `Stop-Service ShiftApp`）。
2. 現在の `DATA_DIR` を**消さずに**別名へ退避（調査用。調査後は安全に廃棄）。
3. 新しい環境にアプリ一式と Node.js を用意（第3章）。
4. 退避先の最新の正常な世代を取り出して `DATA_DIR` に展開：
   - Linux: `tar -xzf shift-app-data-YYYYMMDD-HHMMSS.tar.gz -C /tmp/restore` → 中の `data/` の内容を `/var/lib/shift-app/` へ → `chown -R shift-app:shift-app /var/lib/shift-app; chmod -R go-rwx /var/lib/shift-app`
   - Windows: zip を展開して `DATA_DIR` へコピー → ACL を再適用（`install-windows.ps1` の ACL 設定を参照）
5. サービス起動 → 管理者でログインし、直近の月が開けること・保存できることを確認。
6. **全員のログイン状態は失われる**（再ログインしてもらう）。復元時点以降の保存は失われるため、現場へ「◯日◯時以降の入力をやり直し」を連絡。
7. 事故の原因を確認し、必要なら全職員のパスワード再発行・証明書の更新を検討（漏えい懸念がある場合）。

### 6-4. 復元訓練（半年〜年1回）
- 別のテスト用環境（本番と別のサーバー/フォルダ）に、実データではなく**退避済みバックアップ**を展開して起動し、①ログインできる ②直近の月が開く ③監査ログが読める、を確認。所要時間を記録。
- 訓練環境は終了後、データを安全に削除し、ネットワークに公開しない。

## 7. 障害時対応

| 症状 | 確認・対応 |
|---|---|
| 画面が開かない | サービス稼働（`systemctl status shift-app` / `Get-Service ShiftApp`）→ プロキシ（nginx/IIS）→ 証明書期限 → ディスク空き |
| 「ログインが必要です」が繰り返される | 時刻ずれ（NTP）、Cookieの Secure 設定（HTTPSで開いているか）、`SECURE_COOKIE=1` と公開URLの整合 |
| ログインできない（本人は正しいと言う） | 10分ロックの可能性（監査ログの `login_locked`）。急ぐ場合は `--passwd` で再発行 |
| 「不正なリクエストです（Origin）」 | プロキシ構成で `PUBLIC_ORIGIN` が未設定/不一致。公開URLのOriginと完全一致させる |
| ロックがプロキシ単位で全員に及ぶ・ログのIPが全部同じ | `TRUST_PROXY=1` が未設定、またはプロキシが `X-Forwarded-For` を渡していない |
| 保存で「競合」が出る | 同じ月を他の人が先に保存した。「最新版を取り込む」か「自分の版で上書き」（後述の制約参照） |
| 保存できない（通信エラー） | 画面は自動で再試行。長引く場合はサーバー・ディスク容量を確認。未保存の変更はブラウザを閉じずに待つよう案内 |
| データが壊れた/消えた | 第6章の復元手順。まず**サービスを止めて**被害拡大を防ぐ |
| 不正アクセスの疑い | サービス停止（またはプロキシでアクセス遮断）→ 監査ログの保全（コピー）→ 全員のパスワード再発行 → 法人の個人情報保護方針に定める報告手順（施設長・個人情報管理責任者）。**報告・通知の要否や期限は法人の方針・指定権者の指導を確認** |

## 8. 個人情報保護の観点

1. **アクセス権の棚卸し**：四半期ごとに `--list` を人事の在籍名簿と突き合わせ、退職者・異動者・権限過大を是正。実施記録（日付・担当・是正件数）を残す。
2. **最小権限**：`admin` は最少人数。フロアを越える閲覧が必要な者だけ `manager1`。
3. **持ち出し禁止**：データ（`DATA_DIR`、バックアップ、CSV、`--out` の出力ファイル）を、私物USB・個人のメール/クラウド/チャットに持ち出さない。画面の「閲覧用ファイルを保存」で出力するHTML・Excel貼付用のコピー・勤怠CSV・印刷物も**氏名・勤務・休暇（個人情報）を含む**ため、保存先を施設内の管理された場所（アクセス権を絞った共有フォルダ）に限定し、不要になれば削除。**全職員が閲覧できる配布物になるので、持ち出し・スマホ等での撮影・社外への転送の禁止を職員へ周知**する。配布範囲・伏せ方（休暇の種類をどこまで見せるか）・保管期間は法人の個人情報保護方針で決める（第9章）。
4. **実データを開発・テストに使わない**：テストは架空データのみ。リポジトリ・メール・チャットに実データを載せない。
5. **ログの保管期間**：監査ログ・バックアップの保管期間は法人が決める（第9章）。既定は無期限保持なので、決めたら `AUDIT_RETENTION_DAYS` とバックアップ世代数に反映。
6. **委託先（外部業者・クラウド）に預ける場合の注意**：サーバー保守・バックアップ保管を外部に任せると、個人情報の取扱いの委託にあたる可能性がある。契約（秘密保持・再委託の制限・事故時の報告・返却/廃棄）、委託先の監督、持ち込む端末・保守作業時のデータ閲覧範囲を**法人の方針に従って**整備する。本アプリは外部送信しない設計なので、クラウドへ置く場合は別途の安全対策・合意が必要。バックアップを預ける場合は暗号化し、鍵は法人側で管理。
7. **職員への周知**：操作が記録されること、1人1ID、パスワードの扱い（他人に教えない・付箋に書かない）を周知。
8. **端末の管理**：閲覧する端末の画面ロック、共有端末での確実なログアウト（セッションは最長8時間有効）。
9. **廃棄**：退職者のデータの扱い、サーバー・媒体の廃棄時はデータを復元不能にする（物理破壊・暗号消去等）。

## 9. 方針決定が必要な事項（法人で決める。法令の解釈は本書で断定しない）

| 事項 | 決めること | 反映先 |
|---|---|---|
| 監査ログの保管期間 | 何日/何年保管し、いつ廃棄するか | `AUDIT_RETENTION_DAYS` |
| バックアップの保管期間・世代 | 日次を何世代、月次を何か月、退職者データの扱い | `backup.sh/ps1` の世代数、運用ルール |
| 配布物（出力ファイル）の範囲・伏せ方・保管期間 | 誰に配るか（全職員か部署別か）、休暇の種類をどこまで見せるか、共有フォルダの権限、旧版の回収・削除 | 4-5、運用ルール |
| 確定権限を持つ人 | 誰に `--grant finalize` を付けるか（承認者・記録） | 4-4 |
| 勤務データの保管期間 | 過去月データを保持する期間、廃棄の方法と承認者 | 運用ルール（現状アプリは自動削除しない） |
| 個人情報管理責任者・事故時の報告ルート | 誰が判断し、どこへ報告するか | 第7章の連絡先 |
| 委託・クラウド利用の可否 | 保守委託、バックアップ預け入れの条件 | 契約・第8章 |
| 利用目的・周知 | 職員への通知・掲示の文面 | 個人情報取扱規程 |

→ いずれも **法人の個人情報保護方針（個人情報取扱規程）および指定権者の指導を確認**して決定してください。

## 10. 現時点の制約（運用でカバーする点）
- `data/` のJSONは**平文**（0600権限）。ディスク暗号化（BitLocker/LUKS）と、サーバー・バックアップ媒体の物理管理で守る。
- 同時編集は「後勝ち」（楽観ロック）。10名の編集者が全部署を編集できるため、**同じ部署を同時に編集しない**よう担当を決める。他の人が保存すると30秒以内に「最新版があります（職員ID・時刻）」と通知され、競合時の画面にも誰がいつ保存したか（職員IDと時刻のみ）が出る。
- 確定済みの月は編集できない（423）。直すときは確定権限のある人が解除→修正→再確定→配り直し。
- 単一サーバー構成（冗長化なし）。停止時は復元手順（第6章）。バックアップは日次なので最大1日分の入力を失い得る。
- ログイン状態・ロック状態は `sessions.json` に保存される（トークンはハッシュのみ。0600）。`DATA_DIR` の権限を守ること。
- パスワードの二要素認証・SSO連携はない。IP制限（プロキシ/FW）と併用する。
